# 词库 IO 与界面快照的串行发布

只增加 app 纯 Kotlin 的 VocabularyStateTransactions 与独立测试；没有修改 root 的 AppViewModel、ReaderScreen 或其他共享界面。库方法保护单次文件事务之后，到 Main 发布整个 savedWords 快照之前仍存在调度间隙；MutableStateFlow.update 只保证那次赋值原子，不能判定其中的列表是否已过时。

## 实际失败与最小修复

先把审阅到的 IO→Main 发布次序抽出为未串行化的 helper，使用可控 dispatcher 暂存第一次发布。存储模型使用真实 SavedWord 字段与 MutableStateFlow，IO 操作在同一测试时钟内执行，不依赖睡眠、文件大小或系统调度概率。它证明的是生产发布协议的时序缺口；不是直接对整个 AppViewModel 做设备测试。

9 例中 5 例在未串行化时失败：

| 顺序 | 未串行化结果 |
| --- | --- |
| lookup 得到 go 快照，Main 发布暂停；remove 删除并发布；释放旧 lookup | 磁盘模型空，界面恢复 go |
| lookup 得到旧 reviewCount=7 快照；review 更新为 8/新日期并发布；释放旧 lookup | 界面复习计数/下次日期回退，存储仍为新值 |
| refresh load 得到旧列表；save 新增 study 并发布；释放旧 load | 界面丢掉已保存的 study |
| import 后 load 得到旧 forms；lookup 观察 went 并发布；释放旧 load | 界面丢掉已记忆的新词面 |
| 第一次事务仍挂起，后续事务应排队并取消 | 未加锁时后续 IO/发布提前发生，无法再撤销 |

最小修复是在同一个 Mutex 中完成 withContext(IO) 的事务与 withContext(Main.immediate) 的同步状态发布。修改后原 9 例全绿，未修改四个用户状态期望。其余用例确认 IO 失败传播/释放、配置的 IO/Main dispatcher 与先发布后返回、IO 中取消、已提交 IO 后发布前取消，以及下一次读取不会死锁。取消不转换成成功或失败回滚。

## 接口与 root 接线

```kotlin
val vocabularyTransactions = VocabularyStateTransactions() // 一个 ViewModel 一个实例
val observed = vocabularyTransactions.withLock(
    transaction = { vocabulary.rememberSurfaceForms(entries) },
    publish = { snapshot -> mutableState.update { it.copy(savedWords = snapshot.savedWords) } }
)
if (observed.changed) scheduleAutoSync()
```

构造器允许注入 ioDispatcher（默认 Dispatchers.IO）和 publicationDispatcher（默认 Dispatchers.Main.immediate）；方法为 suspend fun <T> withLock(transaction: suspend () -> T, publish: (T) -> Unit): T。

所有相关路径使用同一实例：lookup 的观察+发布、save、remove、review；review 失败后的实际 load+回滚发布；refresh/import 最后阶段的 vocabulary.load+发布。普通词典查找与非词库准备可以放锁外，避免占用词库事务。onDone、提醒调度、autoSync 在方法返回后调用，publisher 只执行当前 Main 状态更新。不要仅给新 lookup 路径加锁而让其他发布者绕过它。

异常由调用方处理，CancellationException 必须重抛（reviewWord 原 runCatching 的失败回滚同样需要区分取消）。取消可能发生在磁盘事务已提交、Main 尚未发布时；下一次参与事务的读取取得实际落盘数据，此 helper 不回滚已经提交的文件。

保证范围是同一实例的参与调用；不改变词库 schema、复习算法或同步冲突策略。
