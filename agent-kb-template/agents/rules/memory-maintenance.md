# 规则：知识库维护

> 这份知识库是给「下一个没有上下文的 agent」看的。它的价值 = 准确度 × 可检索性，不是篇幅。

## 何时写入

在以下情况**必须**更新 `.agents/memory/`：

1. 花了超过 15 分钟才搞清的事实（架构关系、隐式契约、设备行为）。
2. 踩了坑并修好 —— 写进 `known-pitfalls.md`，结构固定：症状 → 根因 → 现状 → 复现/验证 → 教训。
3. 修改了模块边界、数据存储位置、外部服务契约 —— 同步对应主题文件。
4. 发现记忆文件与代码不符 —— 立刻改正，并在该文件的「最后核对」行更新日期与 commit。

**不要**写入：一次性的调试细节、能从代码一眼看出的东西、猜测（猜测只能进「未验证 / 待查」小节）。

## 怎么写

- 与仓库主文档一致的语言，短句，列表优先。禁止总结性套话（「本模块非常重要」之类）。
- 每条断言附依据：`相对路径`（正斜杠，相对仓库根），必要时带行号或符号名。
- 行号会漂移：优先引用符号名（类名/函数名），行号只作辅助。
- 冲突处理：文档与代码不一致时**以代码为准**，并明确写出「文档 X 声称 A，代码实际 B」。
- 敏感值零容忍：API Key / token / 密码 / 口令一律不写，只写字段名与所在文件。
- 单个文件控制在 200 行内。超了就拆主题，并在 `MEMORY.md` 更新索引。
- **增量追加要回收计数**：新条目用未占用的编号（或日期）命名，不重号；追加后同步文件头与 `MEMORY.md` 索引里的「共 N 条」类数字。
- **同一数值只维护一个权威出处**：条目数、版本号、阈值这类会变的数字，要么只写一处，要么在每处标注权威出处（如「以 AGENTS.md 为准」）；发现两处不一致时按权威出处改齐。

## 文件模板

```markdown
# <标题>

> 面向 agent 的项目记忆，事实来自实际阅读的源码。

**范围**: 一句话
**关键文件**:
- `相对路径` — 作用
**最后核对**: YYYY-MM-DD @ commit <短 sha>

## 架构与数据流
## 关键契约（改动时必须保持）
## 坑与非显然结论
## 如何验证
## 未验证 / 待查
```

## 索引纪律

- 新增记忆文件后**必须**在 `.agents/memory/MEMORY.md` 加一行，写明「文件名 + 一句话它能回答什么问题」。
- `MEMORY.md` 是入口，只放指路与最高价值结论，不放细节。
- 每个条目前的状态标记：`已核对` / `部分过期` / `待重核`。看到 `部分过期` 就顺手修。
- `MEMORY.md` 头部的「最后核对」行取库内各文件「最后核对」的最新值；更新任何记忆文件时同步它。

## 过期治理

- 每次版本号变更（版本配置所在：【构建配置文件】）后，抽查「最后核对」早于上一个版本的文件。
- 大重构之后，**先改记忆再写代码总结**，避免旧结论继续误导。
- 挑一个「多处出现的计数」当金丝雀（如文案资源条数）：偶尔全文检索一遍，出现不同值 = 治理已经衰减，安排一次集中校正。
