# BUG-029 生词高亮用「存储词」替换原文，篡改正文大小写

- 严重程度：🟡 轻微
- 状态：**已修复（代码，`5c36f2c` 2026-09-01）；真机未验**
  —— 回填改用正文原样切片 `span.textContent = match[0]`，不再拿存储词覆盖大小写
- 置信度：高（代码直读可判定）
- 发现日期：2026-09-01
- 来源：静态审查新发现（issue #1 未报，属 BUG-027 同段代码的连带缺陷）
- 涉及文件：`src/app/src/main/java/com/linguareader/app/reader/ReaderScripts.kt`（756、769 行）

## 现象

高亮生词后，正文中该词的**大小写被改写成生词本里存的形式**：
生词本存的是 `apple`，段首的 `Apple` 会被显示成 `apple`。

## 根因

匹配是大小写不敏感的（`lower.indexOf(word.toLowerCase())`），但**回填时用的是
存储词本身**，而不是原文对应区间的文本：

```js
// 756 行：记录的是「存储词」
segments.push({ word: best.word });
...
// 769 行：直接把存储词写回 DOM
span.textContent = segment.word;
```

原文那一段（`remaining.slice(best.index, best.index + best.word.length)`）被丢弃了。

因为是 DOM 文本替换，这个改写还会**污染下游**：
`TranslationMemoryIndex` 的查询串、TTS 的取文、以及再次点词查词，
拿到的都是被改写后的文本。

## 可证伪预测

保存小写 `lantern`，打开含句首 `Lantern` 的章节 → 该词显示为小写；
关闭「语境高亮」开关（`ReaderScreen.kt:472` 的 `reminders.contextHighlight`）
→ 大小写恢复正常。

## 修复建议

改为保留原文切片：

```js
const matched = remaining.slice(best.index, best.index + best.word.length);
segments.push({ word: matched });
```

与 BUG-027 的边界修复在同一个 `while` 循环里，**必须同批修改**，否则会冲突。

## 回归验证

- 断言高亮前后 `content.textContent` 完全一致（只多了 `<span>` 包裹，文本不变）。
  这条可以直接做成 JS 层的自检断言，成本很低。
