# BUG-039 词级对齐的置信度下限恒高于阈值，过滤门槛形同虚设

- 严重程度：🟡 轻微（但直接造成用户可见的「高亮与释义对不上」）
- 状态：待修复
- 置信度：中高（算术可判定；「是否为用户现象的主因」需数据佐证）
- 发现日期：2026-09-01
- 来源：GitHub issue #1 标题补充第 9 条
- 涉及文件：`src/app/src/main/java/com/linguareader/app/translation/WordAligner.kt`
  （19、56–70、93–106、115–119 行）

## 现象

「词级高亮与单词释义不匹配」——点词后，中文译句里被标亮的片段，
和弹层里展示的那条释义对不上。

## 根因

### 1）阈值永远拦不住任何候选

```kotlin
// 60-65 行
val posPenalty = abs(enPos - zhPos) * 0.35        // 上限 0.35
val confidence = (1.0 - posPenalty + bonus).coerceIn(0.0, 1.0).toFloat()
// 70 行
return best?.takeIf { it.confidence >= MIN_CONFIDENCE }   // MIN_CONFIDENCE = 0.40（19 行）
```

`posPenalty` 的**最大值是 0.35**（两个相对位置分别为 0 和 1 时），
所以 `confidence` 的**理论下限是 0.65**，恒大于阈值 0.40。
**这个 `takeIf` 永远为真**，等于没有过滤。

### 2）候选被炸成单字，什么都能命中

```kotlin
// 100-103 行：按 [，,、；;／/·\s] 把义项切碎
// 115-119 行：单字只要是汉字就算合法候选
term.length == 1 -> term[0] in '\u4e00'..'\u9fff'
```

放开单字是为了「洞/水/火」这类词（注释 108–114 行有说明），
但代价是「的/地/上/中/人」这类高频字也成了候选，在译句里几乎必然命中，
唯一的裁决只剩相对位置差。

### 3）候选来自**全部义项**，与用户正在看的那条释义无关

`align` 的 `candidates` 是整个词条的义项集合。于是高亮的中文很可能属于
另一个词性/另一条义项——这正是用户说的「与释义不匹配」。

## 可证伪预测

1. 找一个多义词（如 `light`），点击后观察高亮片段是否来自弹层里排在第一条的释义；
2. 在 `align` 里打日志输出被选中的 `term` 与其来源义项 →
   统计「高亮 term 与展示义项不同源」的比例。**这个比例是本条的量化指标**，
   修复前后必须对比。

## 修复建议

1. **让阈值真正起作用**：要么提高 `MIN_CONFIDENCE` 到 0.65 以上的有意义区间，
   要么把 `confidence` 改成相对度量（如最优分与次优分的差距 / 归一化到 0–1），
   而不是当前这个恒 ≥0.65 的量。
2. **候选按义项分组、与展示义项绑定**：优先只用「当前展示/语境优选那条义项」
   （`ContextAnalyzer.senses` 的 `contextPreferred` 已经算好了）的候选，
   全部落空再回退到其他义项，并把命中来源回传给 UI，让高亮与释义可以互相指认。
3. **单字候选加护栏**：仅当该单字是义项的**完整内容**（而非切碎产物）时才允许，
   或要求单字候选额外满足更严的位置约束。
