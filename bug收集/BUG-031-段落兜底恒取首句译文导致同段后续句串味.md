# BUG-031 段落兜底恒取「该段第一条句对」，同段后续句子串味

- 严重程度：🟠 中等
- 状态：待修复
- 置信度：高
- 发现日期：2026-09-01
- 来源：GitHub issue #1 标题补充第 4 条（与 BUG-030 同现象、不同根因）
- 涉及文件：`src/app/src/main/java/com/linguareader/app/translation/TranslationMemoryIndex.kt`
  （段落兜底 89–91 行，三级重叠 62–66 行，`toResult` 116–128 行）

## 现象

「位于 A 句后的 B 句返回 A 句意思」。BUG-030 从**生产端**（对齐时丢句/错位）解释了
一部分，本条是**查询端**的独立第二条路径——即使对齐档案是对的，查询也会串味。

## 根因

### 1）第 5 级段落兜底取 `firstOrNull`

```kotlin
// 89-91 行
entries.firstOrNull { it.paragraph == nParagraph }
    ?.takeIf { it.pair.confidence >= TranslationMemorySearch.MIN_ACCEPT_CONFIDENCE }
    ?.let { return toResult(it, TranslationMatchLevel.PARAGRAPH) }
```

**段落内任何一句没能精确命中，都会返回该段的第一条句对**。而 `toResult` 又是：

```kotlin
// 121 行
chinese = pair.zhSentence.ifBlank { pair.zhParagraph },
```

所以 `PARAGRAPH` 级兜底实际吐出的是**首句译文**，而不是整段译文。用户点第 3 句，
拿到第 1 句的意思——正是「B 句返回 A 句意思」。

### 2）第 3 级「句子重叠」用双向 `contains`

```kotlin
// 62-66 行
(it.sentence.contains(nSentence) || nSentence.contains(it.sentence))
```

短句（`"He nodded."`）会被任意包含它的长句吃掉，同样返回别人的译文。

### 3）为什么精确命中会失败（上游诱因）

第 1、2 级要求归一化后**完全相等**。查询串来自 WebView 端 JS 的切句，
档案里的句子来自 Kotlin 端 `tts/SentenceSplitter`。两端切句口径只要差一个弯引号、
一个缩写点（`SentenceSplitter` 有 `protectedPeriods` 处理，JS 侧未必有），
就掉到第 4 级模糊（阈值 `FUZZY_MIN_SIMILARITY = 0.85` 的 token-set Jaccard，偏严），
再掉到第 5 级兜底。

## 可证伪预测

1. 点段落里第 2、3 句 → 返回的中文与点第 1 句完全相同；
2. 在 `lookup` 里加临时日志打印命中级别，点 100 次统计分布：
   如果 4/5 级占比很高，说明「两端切句口径不一致」是主要诱因；
   如果 1/2 级占比很高但仍串味，说明问题在 BUG-030 的对齐产出。

**这个统计应该在动手改任何代码之前做**，它决定了到底该修对齐器还是修阈值。

## 修复建议

1. **段落兜底不要吐首句译文**：`PARAGRAPH` 级应返回 `zhParagraph`（整段），
   让 UI 明确呈现为「段落级对照」，而不是伪装成句子级的错误译文。
2. **段落内按位置挑**：兜底时用查询句在段落内的序号/字符偏移，
   挑序号最接近的那条句对，而不是无脑 `firstOrNull`。
3. **三级重叠加长度护栏**：只有在 `min(len) / max(len) >= 0.6` 之类的比例下才接受包含关系。
4. **统一切句口径**：把 JS 侧切句换成与 `SentenceSplitter` 一致的规则（或反过来，
   查询前把句子交给 Kotlin 侧重新切一次再归一化）。这条治本，但改动面最大。
