# BUG-028 生词按原型/短语存储，变形词与跨节点短语无法划线

- 严重程度：🟠 中等
- 状态：待修复
- 置信度：高（静态阅读定位；需真机确认短语场景）
- 发现日期：2026-09-01
- 来源：GitHub issue #1 标题补充第 7、8 条
- 涉及文件：
  - `src/app/src/main/java/com/linguareader/app/data/VocabularyRepository.kt`（97–103 行）
  - `src/app/src/main/java/com/linguareader/app/ReaderScreen.kt`（472 行）
  - `src/app/src/main/java/com/linguareader/app/reader/ReaderScripts.kt`（728–734 行）
  - `src/app/src/main/java/com/linguareader/app/data/Models.kt`（`SavedWord` 114–165 行）

## 现象

1. 「对于去掉一些字母变形的单词加入生词后无划线」：正文里点 `studies` 收藏，
   之后整本书里的 `studies` **一处都不划线**。
2. 「为短语中的一个词加入生词本后无划线」：在短语里点某个词收藏，该短语不划线。

用户在 issue 里推测两者同因，**推测正确，但不是 BUG-027 的边界问题**，是存储口径问题。

## 根因

### 1）存进生词本的是原型或整条短语，不是点击时的表面形

```kotlin
// VocabularyRepository.kt:97-98
val headword = entry.matchedPhrase ?: entry.headword
val id = headword.lowercase(Locale.ROOT)
```

而高亮下发的正是这个字段：

```kotlin
// ReaderScreen.kt:472
savedWords = if (reminders.contextHighlight) savedWords.map { it.headword } else emptyList(),
```

于是 JS 拿到的是 `study`，正文里是 `studies`。`study` 与 `studies` 的公共前缀只有
`stud`（`stud-y` vs `stud-i-es`），**连子串都不是**，`indexOf` 直接失配 → 完全无划线。

对比 `running`/`run` 这种「原型是正文的前缀」的情况，子串能命中，所以表现成
BUG-027 的「只划出原型部分」——**同一个存储缺陷，在两类词形上表现不同**，这解释了
为什么用户把它报成了两条。

### 2）短语匹配还多一层：JS 是逐文本节点匹配的

```js
// ReaderScripts.kt:728-734
const walker = document.createTreeWalker(root, NodeFilter.SHOW_TEXT);
```

匹配在**单个文本节点内**进行。短语一旦跨行内元素（`<em>look</em> after`）、
跨换行、或正文里是多空格/软换行分隔，节点内文本就对不上存储的单空格短语，必然失配。
短语同时还会遇到 (1) 的变形问题（`looked after` vs `look after`）。

## 可证伪预测

1. 收藏 `studies`（词典原型 `study`）→ 生词本条目显示为 `study`，正文 `studies` 无划线；
2. 收藏一个正文中**恰好等于原型**的词（如 `lantern`）→ 划线正常；
3. 构造一段 HTML 让短语跨 `<em>` 边界 → 即使短语原样出现也不划线。

第 1、2 条的对比是关键：如果原型词也不划线，那问题不在存储口径，本假设作废。

## 修复建议

分两步，第一步就能消掉大部分用户可感知的问题：

**第一步（不改存储）**：下发高亮词表时同时下发表面形。
`DictionaryRepository` 已有 `surfaceWord`（`data/DictionaryRepository.kt:63`）与
`lemmaCandidates`（129 行起，走 `ecdict.sqlite` 的 `f.lemma` 反查表）。
把「原型 → 该书出现过的表面形集合」一起传给 `ReaderScripts.savedWordsScript`。
注意 `ReaderController.kt:43` 与 `ReaderScripts.kt:726/1061` 各有一处
`take(300)/slice(0,300)` 上限，扩表后要重新评估这个预算。

**第二步（改存储，有迁移）**：`SavedWord` 增加 `surfaceForms: Set<String>` 字段。
`Models.kt:129-165` 是手写 JSON 序列化，**必须保证旧档案缺字段时能读出**
（`optJSONArray` + 空集合兜底），否则老用户生词本会炸。

**短语跨节点**：把逐节点匹配改成「先把 root 的文本节点串成一条带偏移映射的长字符串，
匹配后再切回各节点」；或退一步，短语只在同一叶块（`p/li/h*`）内匹配。
后者实现成本低得多，建议先做后者。
