## B. 已定位根因的修复方案

### B1 🔴 生词划线四合一（主1 + 补2 + 补7 + 补8）——**一处改动消掉 4 条 issue**

**根因（两个因素叠加）**：

1. **只存原型**：`VocabularyRepository.kt:97` `val headword = entry.matchedPhrase ?: entry.headword`，`Models.kt:114-131` 的 `SavedWord` **没有任何表面形字段**——用户在正文里点的是 `studied`，存进去的是 `study`。
2. **纯子串匹配**：`ReaderScripts.kt:747` `const index = lower.indexOf(word.toLowerCase());` —— 无词边界、无词形还原。

这两条组合起来，恰好**精确复现** issue 描述的三种症状：

| 原型与正文的关系 | 结果 | 对应 issue |
|---|---|---|
| 原型是正文词的前缀（run → running） | 只给 `run` 画线，`ning` 没画 | **补2「只画了原型的部分」** |
| 原型不是前缀（study → studied、city → cities） | 完全画不上 | **补8、补7** |
| 原型出现在无关词内部（app ⊂ apple） | 画错地方 | **主1** |

**修复方案（两步，缺一不可）**：

**第 1 步 · 存表面形**。`ContextAnalyzer.kt:33-34` 里 `surfaceWord` 与 `headword` 本来就同时存在，只是入库时丢了表面形。给 `SavedWord` 加一个字段（**注意 `Models.kt` 的 `toJson/fromJson` 要同步，且 `fromJson` 必须对老数据给默认值，否则老书架会解析失败**）：

```kotlin
data class SavedWord(
    ...
    /** 入库时正文里的原始形态；老数据为空时回退到 headword。 */
    val surfaceForms: List<String> = emptyList(),
)
```

**第 2 步 · 用词边界 + 词形变体匹配**。把 `markSavedWords` 的三重循环整体换成**一次正则扫描**——顺带把审查报告 §5.4 记的性能问题（每节点 × 300 词 × `guard<1000`，还反复 `toLowerCase()` 整段）一起解决：

```js
// 生成：\b(phrases|longer|words)\b，长的排前面保证优先匹配短语
function buildSavedPattern(words) {
  const variants = [];
  for (const w of words) {
    const base = String(w || "").trim();
    if (base.length < 2) continue;
    variants.push(base);
    if (/^[a-z]+$/i.test(base)) variants.push.apply(variants, inflect(base));
  }
  if (!variants.length) return null;
  variants.sort(function (a, b) { return b.length - a.length; });
  const alt = variants.map(function (v) {
    return v.replace(/[.*+?^${}()|[\]\\]/g, "\\$&").replace(/\s+/g, "\\s+");
  }).join("|");
  return new RegExp("\\b(" + alt + ")\\b", "gi");
}

// 规则式英文变体：run -> runs/running/ran 这类靠词典，规则只覆盖高频规整变化
function inflect(w) {
  const out = [w + "s", w + "es", w + "ed", w + "ing"];
  if (/[^aeiou]y$/.test(w)) out.push(w.slice(0, -1) + "ies", w.slice(0, -1) + "ied");
  if (/e$/.test(w)) out.push(w.slice(0, -1) + "ing", w + "d");
  return out;
}
```

**关键取舍**：`\b` 只对 ASCII 字母有效，英文阅读器足够；但**连字符词（`well-known`）与撇号（`don't`）要单测覆盖**。规则式变体会漏不规则动词（go/went），所以**第 1 步的表面形入库才是主力**，正则变体只是兜底。

**验证**：`ReaderScriptsTest.kt` 已有 JS 行为测试的先例，为这段加断言——`app` 不得命中 `apple`；`study` 要命中 `studied`；`run` 命中 `running` 时要画**整词**而不是前 3 个字母。

### B2 🔴 长文本整本 AI 翻译总是失败（主2）

**根因链（三段放大）**：

1. **数字锚点零容忍**：`AiBookTranslator.kt:142-146`
   ```kotlin
   Regex("\\d+").findAll(source).forEach { match ->
       if (match.value !in translated) throw AiRequestException("AI 译文丢失了数字锚点「${match.value}」")
   }
   ```
   模型把 `1,000` 译成 `一千`、把 `19` 并进 `十九世纪`，就判失败。长文里数字极多，**每批命中一次的概率随批数累积**。
2. **长度比例检查**同样是硬失败（`:160-164`，`<0.2×词数` 或 `>8×词数`）——中英信息密度差异大，长段落偶发越界。
3. **一批失败 = 整本中止**：`AiTranslationRepository.kt:88-101` 异常直接冒泡出 `translateBook`；`:267-294` 只重试一次且**无退避**。

于是「文本越长越必然失败」——与 issue 描述完全一致。

**修复方案（按收益排序）**：

1. **把整本任务从"全或无"改成"逐批容错"**（收益最大）：单批用尽重试后，**记下该批失败、保留原文、继续下一批**，全书结束时汇总「N 段未翻译，可重试」。检查点已按批落盘（`:280-283`），天然支持"补跑失败批"。
2. **数字锚点降级为软校验**：仅在**第一次**失败时进重试 prompt 提醒模型；重试后仍不符就**放行并记警告**，不再抛异常。另可放宽为「阿拉伯数字或其中文数词等价形式出现即算通过」。
3. **重试加指数退避并识别 429/5xx**：现在是立刻重发，命中限流时等于二次撞墙。
4. 顺带修 `readTimeout = 300_000`（`JsonChatTranslator.kt:113-114`）配合取消（见 B6）。

**验证**：`ai/` 下已有 16 个单测，为 `extractValidated` 补「数字被译成中文数词时不再抛异常」「单批失败不影响其余批次」两条。

### B3 🔴 听书与阅读互相回退进度（我的发现；疑似也是补6/主5 的一部分成因）

**根因**：`LibraryRepository.kt:45-68` 的 `saveProgress` / `saveListeningProgress` 都是 `writeMetadata(book.copy(...))`——**拿调用方传进来的整份 `Book` 快照覆盖整个 metadata.json**，而两个写入方各持一份过期快照（阅读侧 `ReaderScreen.kt:284-287` 每 800ms、听书侧 `TtsPlaybackService.kt:406-414` 起播时的 `EXTRA_BOOK_JSON`）。

**修复方案**：写入不再信任调用方快照，改成**锁内读-改-写**，且每个方法只碰自己负责的字段：

```kotlin
private fun readMetadata(bookId: String): Book? {
    val f = File(File(booksDir, bookId), "metadata.json")
    return if (!f.isFile) null else runCatching { Book.fromJson(JSONObject(f.readText())) }.getOrNull()
}

suspend fun saveProgress(book: Book, chapterIndex: Int, pageIndex: Int, progress: Float) =
    withContext(Dispatchers.IO) {
        mutex.withLock {
            val latest = readMetadata(book.id) ?: book   // 盘上最新，不是调用方快照
            writeMetadata(latest.copy(
                chapterIndex = chapterIndex,
                pageIndex = pageIndex,
                progress = progress.coerceIn(0f, 1f)
            ))
        }
    }
```

`saveListeningProgress` 同理只改 `ttsChapterIndex/ttsSentenceIndex`；`saveTranslation` 只改三个译本字段（它耗时数十秒到数分钟，回写时抹掉期间阅读进度的问题也一并解决）。

**顺带修同文件的两处**：
- `:104-107` `renameTo` 失败的回退是**非原子直写**，崩溃会留下截断 JSON → 落进 `:31` 的 `getOrNull()` → **书静默从书架消失**。回退路径应保留 `.tmp` 并**报错**，不要静默吞。
- `:110-119` `migrateLegacyMetadata` 的 `.map` 是急切求值 + 空 `catch`：v1 数据里**一条坏记录就让整批迁移放弃**且旧文件不删，老用户书架会永久为空。改成逐条 `mapNotNull` + 记录失败条目。

**验证**：写一条 JVM 单测——模拟"听书侧写入后，阅读侧用旧快照写入"，断言 tts 两字段不被回退。

## C. 需要另一路定位结果才能动的

### C1 ⚠️ 主5 / 主6（听书翻页）——动手前必读

`AGENTS.md` 的验证纪律里有一条**明令禁区**：

> **TTS 高亮的分页跟随是禁区**：`ReaderScripts.kt` 的 `followRangeIntoView` 只允许滚动模式；分页模式翻页会触发阅读器位置回报，与引擎形成反馈回路导致**章末死循环**（2026-08-23 真机事故，轨迹与根因见 VALIDATION.md 当日条目）。要做分页跟随必须先设计桥接标记抑制位置回报。

主6「听书时不能自动翻页」**正是这条禁区的直接后果**——它不是疏漏，是为了躲一个已知的死循环而故意不做的。所以：

- **不要**直接给分页模式加 `followRangeIntoView`；
- 正确做法是先做**桥接抑制位**（翻页由 TTS 触发时，屏蔽这次的位置回报，避免回路），再开跟随；
- 主5「手动翻页跳回当前页第一句」很可能与同一处回报回路同源，建议**和主6 一起定位、一起修**，别分开改。

### C2 🟡 补6 进入滑动状态丢进度、翻到章首

**我的推测（需运行时确认）**：`ReaderScripts.kt:310-318` 的 `enterScrollMode` 里，`applyScrollLayout()` 之后**同一 tick** 就调 `syncScroll()`；而 `syncScroll()`（`:300-308`）算的是

```js
const max = scroller.scrollHeight - scroller.clientHeight;
scroller.scrollTop = max > 0 ? scrollRatio * max : 0;   // max<=0 就落到 0 = 章首
```

布局刚从横向分栏切成纵向滚动，**浏览器还没重排**，`scrollHeight` 可能仍是旧值 → `max <= 0` → `scrollTop = 0` → **跳章首**。

**验证方法**：在 `syncScroll()` 里打印 `scrollHeight/clientHeight/scrollRatio`，看切换瞬间 `max` 是不是 ≤0。

**若确认**：把 `syncScroll()` 推迟到重排后（双 `requestAnimationFrame`，或先强制读一次 `scroller.offsetHeight` 触发同步重排），并在 `max<=0` 时**不要**写 `scrollTop=0`，而是保留 ratio 等下一帧重试。

### C3 🟡 补10 词性 adj 标成 a

`ContextAnalyzer.kt:231-241` 的 `sensePartOfSpeech` **本身是对的**（`a.` 与 `adj.` 都映射到 `ADJECTIVE`）。所以用户看到的 `a` 大概率是**词典释义原文里的缩写被直接显示**，而不是走了 `PartOfSpeech` 枚举的 `labelRes`。
